2. The flow

question + session_id + employee_id
  | load session memory (last 6 turns) ; load profile via get_my_profile (code, not the model)
  v
PLAN  (planner_v3, schema Plan)             malformed JSON twice -> fallback plan: route policy, search the question
  | route
  |-- clarify / refuse_pii / out_of_scope --------------------+
  |-- escalate -> escalate_to_hr (H6) -------------------------+
  |-- refuse_injection -> one policy_search on the question    |
  '-- policy / hrms / policy_and_hrms                          |
        v                                                      |
     EXECUTE loop (executor_v1, native tool calls)             |
        tools offered depend on the route                      |
        repeated call -> blocked; 2nd repeat -> leave loop     |
        bad args / unknown tool / tool error -> fed back       |
        "DONE", step cap or token budget -> leave loop         |
        v                                                      v
ANSWER (answer_v2, schema FinalAnswer, passages best first, trimmed to the token budget)
  | code checks: check_citations + unsupported_numbers
  | problem -> ONE revision call with the problem shown
  | still wrong -> drop bad citations; an "answer" with none left becomes refuse_not_in_corpus
  v
CRITIC (critic_v2): advisory by default, logged only
  v
AgentResponse: answer, citations, steps (trace), tool_calls, status, usage

3. Decisions (all accepted 20 Nov)

#DecisionWhy
1Step = one planner, executor, tool, answer-revision or critic action. Total cap 10. At the cap, skip to ANSWER with what was gathered; the trace says step_cap.The brief says "10-step cap".
2Critic config off | advisory | revise; default advisory.Dev runs showed it flags correct drafts. H9 measures V3 with and without it.
3Unverifiable citations downgrade to "could not verify"; switch STRICT_CITATIONS.Grounded answers, at a possible cost in recall; H9 measures it.
4Tools offered depend on the route: policy gets policy_search; hrms gets the HR tools; both gets both.An 8B model choosing from 10 tools is a likely failure.
5First executor call uses tool_choice="required"; later calls "auto".Stops answering from memory. Verified in the 20 Nov probe.
6Session memory: prepend "Earlier in this conversation: ..." (last 3 turns, about 300 tokens, marked untrusted) to the question string.The frozen prompts stay unchanged.
7Identity: actor_id always comes from the request. Any employee_id argument from the model is removed before the call.Existing design rule; gets a test.
8Eval variants v2_rag (search once, answer prompt, citation check) and v3_agent are registered in H5.About 40 lines; H9 only runs them.

5. Failure modes and their tests

Unknown tool namerun_tool error fed back; counted as a step
Tool raises or returns ok: falseRecorded in tool_calls with the error; loop continues; answer is not cited from it

Prompt too big for 8192Passages trimmed; test with 50 long passages

Answer is malformed JSON twiceSafe fallback message, status=error, raw text in the trace
Invented quote or numberOne revision with the problem shown; then downgrade (strict citations)

Model tries to pass an employee_idIgnored; the session's id is used
Draft createdstatus=needs_confirmation; nothing submitted
Session memoryPersists across turns, capped at 6 turns, purge works

6. Risks and what cannot be verified before a real run

  • How well Qwen3-8B calls tools. The probe showed tool calls are populated, not that the choices are good. Fallbacks in order: narrower tool lists per route (already in), required on every executor step, then a JSON-action schema instead of native calls.
  • Latency. About 4 to 8 calls per question at about 2 s each, so 8 to 16 s. A full V3 run (80 items x 3 repeats x about 8 calls) is roughly 1 hour. Plan it for Tue 24 at the latest; the cache helps reruns.
  • Dev passages are hand-picked, so dev results will look better than real retrieval will.
  • Not yet reviewed by a human: the gold answers, the scorer spot checks and the dev set.
